# Vulkan validation findings that existed BEFORE the guard was switched on (#1704).
#
# Format:  <message id> | <one-line reason, with the issue tracking it>
#
# Rules, and they matter more than the list:
#
#   * Every entry is a DEFERRED DEFECT, not an accepted one. Each line names an open issue.
#     Nothing here is "fine"; it is "known, written down, and not fixed in the PR that measured it".
#   * A bare id with no reason is rejected by the scanner. An unexplained filter reads as
#     "handled" when it is not, which CLAUDE.md calls out as worse than a loud gap.
#   * Adding a line is a decision to defer, and it should come with an issue. Deleting a line
#     is what fixing the defect looks like.
#   * The scanner reports — but does not fail on — entries that produce no messages in a given
#     run, because the observed set is genuinely driver-dependent (see the two notes below).
#
# Measured baseline, 2026-08-01, on the whole ctest suite:
#
#   Ubuntu 24.04 / validation layers 1.3.275.0 / Mesa 25.2.8 lavapipe   (the CI runner's exact
#     driver, reproduced in `podman run --rm ubuntu:24.04`):  7 ids, 187 messages, 166/166 pass
#   Fedora 44 / validation layers 1.4.341.0 / Mesa 26.1.4 RADV (STRIX_HALO):  9 ids, 51 messages
#
# The two ids the CI environment does not produce are marked below. Neither is absent because it
# was fixed: `maintenance4-08602` is a newer check than layer 1.3.275, and `size-01389` cannot
# trigger on lavapipe, whose nonCoherentAtomSize is 1. Both are real on hardware.

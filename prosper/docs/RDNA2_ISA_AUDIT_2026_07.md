# RDNA2 ISA audit - recompiler vs AMD reference guide (2026-07)

A systematic sweep of the RDNA2->SPIR-V shader recompiler (`src/gpu/rdna2_decode.cpp`,
`src/gpu/rdna2_to_spirv.cpp`) against the official AMD "RDNA 2 Instruction Set Architecture
Reference Guide" (document 70648), run against master `5d0fddf` on 2026-07-18.

## Method

Eight area-scoped reviewers (instruction decode; scalar ALU; vector ALU; VOPC/modifiers;
SMEM/MUBUF/DS memory; MIMG/EXP/VINTRP; EXEC/VCC/control-flow structurizer; operand and
inline-constant semantics) each compared their slice of the recompiler with the matching ISA
chapters (searchable pdftotext extraction, with the original PDF for garbled tables). Every
candidate finding was then re-derived by an independent adversarial verifier instructed to
refute it (misread code, misread ISA, deliberate evidence-backed PS5 deviation, unreachable
path, duplicate of a tracked issue) before acceptance. Unimplemented-but-cleanly-rejected
instructions were excluded by design: the recompiler is intentionally partial and fail-visible,
so only silently-wrong-results defects were accepted.

Result: 43 confirmed findings (37 unique after cross-area dedup - 6 defects were found
independently by two reviewers), 4 candidate findings refuted by verification, 0 left uncertain.

## gpu-audit ISA sweep: rdna2_decode - 7 findings (MUBUF/MIMG opcode-bit truncation, missing literal lengths) (#878)

### 1. [HIGH] MUBUF opcode masked to 7 bits: D16 format ops (128-135) silently alias onto 32-bit format ops (0-7)

**Location:** `prosper/src/gpu/rdna2_decode.cpp:375`

**What the code does:** i.opcode = (w >> 18) & 0x7Fu extracts only 7 bits for MUBUF. BUFFER_LOAD_FORMAT_D16_X (op 128) therefore decodes as opcode 0 = BUFFER_LOAD_FORMAT_X, D16_XY (129) as XY (1), and the D16 stores 132-135 as stores 4-7. Stage 2 (rdna2_to_spirv.cpp:4114-4124 and the coverage gate at :6878 'opcode <= 0x07u') ACCEPTS opcodes 0-7, so a D16 buffer-format op is silently translated as its 32-bit twin: the hardware op writes packed f16 halves (one VGPR per 2 components) while the translation writes one f32 per component — wrong data layout and wrong register footprint, no rejection.

**What the ISA says** (Table 98 'MUBUF Fields': OP is [25:18] (8 bits); Table 99 'MUBUF Opcodes' (p.274-275)): OP [25:18] Opcode; Table 99 lists 128 BUFFER_LOAD_FORMAT_D16_X, 129 ..._D16_XY, 130 ..._D16_XYZ, 131 ..._D16_XYZW, 132-135 BUFFER_STORE_FORMAT_D16_X..XYZW

**Suggested fix:** Use i.opcode = (w >> 18) & 0xFFu; in the MUBUF case. Stage 2's existing opcode whitelists (<= 0x07 etc.) then automatically fail-visibly reject the D16 variants until they are modeled.

**Verifier corrections/refinements:** Finding is accurate as filed (file, line 375, severity, fix all correct). Minor additions: the field-width comment at rdna2_decode.cpp:371 ('opcode[24:18]') should be corrected to [25:18] along with the mask; the stage-2 acceptance range is rdna2_to_spirv.cpp:4104-4127 (switch) plus the coverage gate at :6878. Note BUFFER_LOAD_FORMAT_D16_HI_X (38) and BUFFER_STORE_FORMAT_D16_HI_X (39) are below 128 and already fail-visibly rejected by stage 2's default case, so only 128-135 are affected.

**When a real shader hits this:** Latent until a title's shader actually emits a D16 buffer-format op. None of the currently-exercised titles has been shown to use them (no D16 handling or dump evidence exists in the repo), and compilers typically emit D16 buffer ops only for f16/unorm16 buffer I/O with 16-bit registers enabled. But PS5 shaders do use packed f16 ALU (VOP3P is modeled), so f16 buffer traffic is plausible in future titles; when hit, the result is silently wrong vertex/buffer data plus clobbered VGPRs (loads) or wrong-width memory writes (stores) with no rejection or diagnostic — the worst failure mode for this recompiler's fail-visible design.

### 2. [MEDIUM] MUBUF LDS bit (bit 16) not decoded: buffer-load-to-LDS misdecodes as a VGPR load instead of being rejected

**Location:** `prosper/src/gpu/rdna2_decode.cpp:383`

**What the code does:** MUBUF decode packs only OFFSET/OFFEN/IDXEN into i.literal and ignores instruction bit 16 (LDS). A buffer_load_* with LDS=1 therefore decodes identically to the plain form, and rdna2_to_spirv.cpp:4096ff emits a normal VGPR load: the VDATA VGPRs get clobbered with fetched data (hardware leaves them untouched) and the LDS write the shader expects never happens — a silent misdecode rather than a fail-visible reject.

**What the ISA says** (RDNA 2 ISA Reference Guide, Table 98 'MUBUF Fields' (sec. 13.6, p.272): LDS [16]; also sec. 8.1 field list (p.57)): LDS [16]: '0 = normal, 1 = transfer data between LDS and memory instead of VGPRs and memory.' Sec 8.1: 'LDS 1 MUBUF-ONLY: 0 = Return read-data to VGPRs. 1 = Return read-data to LDS instead.'

**Suggested fix:** Capture bit 16 in the decoded instruction (e.g. i.literal bit 14 or a dedicated flag) and reject (ok=false) in the MUBUF emitter when it is set, so buffer-to-LDS transfers stay fail-visible until implemented.

**Verifier corrections/refinements:** Finding is accurate. Minor citation correction: Table 98 "MUBUF Fields" is in sec. 13.6.2 (MUBUF), p. 274 of the guide, not sec. 13.6/p. 272 (13.6 opens the Vector Memory Buffer Formats chapter at p. 272; 13.6.1 is MTBUF). Line 383 is the literal-packing statement; the omission spans the whole MUBUF decode case at rdna2_decode.cpp:370-384. Suggested fix stands: literal bits 14/15 (or 16, mirroring the hardware position) are unused for MUBUF, so the LDS bit can be captured there or in a dedicated flag, and the MUBUF emitter in rdna2_to_spirv.cpp (case at line 4096) should set ok=false when it is set. Severity medium is appropriate (see exercised_impact).

**When a real shader hits this:** Buffer-load-to-LDS is a compute-shader prefetch idiom (wave-cooperative staging of buffer data into workgroup memory). Mainstream game shader compilers emit it rarely; none of the currently exercised prosper titles are known to hit it (no LDS-form MUBUF appears in the project's test corpus or documented capture findings). But prosper does execute real compute kernels now (Dead Cells fill/format-copy dispatches), so the encoding is plausibly reachable as title breadth grows. When hit, the failure is fully silent: a VGPR that the shader may still be using (VDATA holds the M# selector, typically an active register) gets clobbered, and the subsequent ds_read of the expected LDS data returns stale/garbage values — classic hard-to-localize corruption rather than a visible recompile reject. Medium severity (latent today, silently wrong when exercised) is the right call.

### 3. [MEDIUM] MIMG opcode MSB (instruction bit 0) ignored: ops >= 128 alias onto ops 0-127; IMAGE_MSAA_LOAD is silently accepted as IMAGE_LOAD

**Location:** `prosper/src/gpu/rdna2_decode.cpp:391`

**What the code does:** i.opcode = (w >> 18) & 0x7Fu reads only bits [24:18]. Per the ISA the MIMG opcode is 8 bits with its MSB in instruction bit 0. IMAGE_MSAA_LOAD (128) therefore decodes as opcode 0 = IMAGE_LOAD, which stage 2 accepts including dim 6 2D_MSAA (rdna2_to_spirv.cpp:6863-6864) -> silently wrong fragment/data semantics. IMAGE_SAMPLE_D_G16 (162) / C_D_G16 (170) etc. misidentify as the 32-bit-gradient sample_d family (currently rejected, but under a wrong identity), and IMAGE_BVH_INTERSECT_RAY (230/231) misidentifies as 0x66/0x67.

**What the ISA says** (Table 100 'MIMG Fields' (p.276): OP [0],[24:18]; Table 101 'MIMG Opcodes' (p.277-278)): OP [0],[24:18] Opcode. See table below. (combine bits zero and 18-24 to form opcode). Table 101: 128 IMAGE_MSAA_LOAD, 162/163/170/171/178/179/186/187 IMAGE_SAMPLE_*_G16, 230/231 IMAGE_BVH[64]_INTERSECT_RAY

**Suggested fix:** i.opcode = ((w & 1u) << 7) | ((w >> 18) & 0x7Fu); stage 2's opcode checks then reject MSAA_LOAD/G16/BVH fail-visibly instead of silently translating the aliased op.

**Verifier corrections/refinements:** The rdna2_to_spirv.cpp citation should be lines 4539-4553 (storage-image path: dim 6 2D_MSAA accepted with ms=true at line 4549, load emitted at 4568-4574), not 6863-6864 (that region is only the deferred-variant instruction counter). Decode file/line (rdna2_decode.cpp:391), severity (medium), and suggested fix (i.opcode = ((w & 1u) << 7) | ((w >> 18) & 0x7Fu), letting stage 2's existing opcode gates reject ops >= 128 fail-visibly) are all correct as stated.

**When a real shader hits this:** Currently latent for the exercised titles: The Messenger, Dead Cells, and Blasphemous 2 are 2D Unity/heaps-style renderers whose captured shaders use image_sample*/image_load/image_store, and stage 2 additionally requires resolved T# provenance, so an IMAGE_MSAA_LOAD reaching the silent-wrong storage-MSAA path has not been observed. It would bite on any future title using MSAA resolve/fmask-style compute passes (IMAGE_MSAA_LOAD, silently wrong sample/component layout in rendered output) or hardware raytracing (BVH ops misidentified). The G16 sample aliases would today only mislabel rejected-shader diagnostics (shader_inspect / capture v7 failed-stage records), not corrupt output.

*Independently reported by both the `decode` and `mimg-exp-vintrp` reviewers.*

### 4. [MEDIUM] V_FMAMK_F16 / V_FMAAK_F16 mandatory 32-bit literal K not counted: instruction length 1 instead of 2, desyncing the decode walk

**Location:** `prosper/src/gpu/rdna2_decode.cpp:484`

**What the code does:** The forced-literal list for VOP2 K-ops covers only 0x20/0x21 (gfx10.1 v_madmk/madak_f32) and 0x2C/0x2D (v_fmamk/fmaak_f32). The f16 forms V_FMAMK_F16 (opcode 55 = 0x37) and V_FMAAK_F16 (56 = 0x38) always carry a trailing 32-bit literal K but decode as 1 dword, so the K constant is re-decoded as a phantom instruction and every subsequent pc/branch target in the stream is wrong. The shader itself would be rejected on the unimplemented opcode, but pure walkers (rdna2_walk consumers such as rdna2_sload_required_bytes and shader_inspect PC/branch decoding) silently misparse everything after the K.

**What the ISA says** (Table 75 'VOP2 Opcodes' (p.248): 55 V_FMAMK_F16, 56 V_FMAAK_F16; instruction descriptions 'Multiply a FP16 value with a literal constant and add a second FP16 value' / 'Multiply two FP16 values and add a literal constant'; section 6.3 literal-usage list naming all four FMAMK/FMAAK ops): 55 V_FMAMK_F16: Multiply a FP16 value with a literal constant and add a second FP16 value; 56 V_FMAAK_F16: Multiply two FP16 values and add a literal constant. Both take a mandatory literal following the instruction.

**Suggested fix:** Add op == 0x37u || op == 0x38u to the mandatory-literal condition at rdna2_decode.cpp:484.

**Verifier corrections/refinements:** Finding is accurate as stated. File/line correct (condition spans rdna2_decode.cpp:483-484). Severity medium is appropriate. Suggested fix correct: add `op == 0x37u || op == 0x38u` to the forced-literal condition; the semantics stage will still fail-visibly reject the unimplemented f16 K-op, but walkers stay in sync. Optionally update the comment listing "the four K-carrying VOP2 mul-adds" to six.

**When a real shader hits this:** Not exercised by any currently observed live-title shader (the semantic stage has never needed VOP2 0x37/0x38, and no dump/test contains them). If a future title ships an fp16 K-op: the recompiler itself rejects the shader fail-visibly at the unknown opcode, but every pure-walk consumer — rdna2_sload_required_bytes (SGPR preload sizing in gpu_executor.cpp:2384), gpu_capture instruction retention, shader_inspect PC/branch-target decode — silently desyncs from the K dword onward, producing wrong instruction boundaries, phantom instructions, and wrong branch targets for the remainder of the stream.

### 5. [MEDIUM] SOPK S_SETREG_IMM32_B32 trailing literal not counted: SOPK is always decoded as 1 dword

**Location:** `prosper/src/gpu/rdna2_decode.cpp:493`

**What the code does:** The SOPK classification unconditionally sets len_dwords = 1. S_SETREG_IMM32_B32 (SOPK opcode 21) carries a mandatory 32-bit literal (the data written to the hardware register), so its literal dword is re-decoded as a phantom instruction and the rest of the stream misparses (same desync class as the FMAMK finding). Compilers emit s_setreg_imm32_b32 in prologs to program MODE (round/denorm), so this can appear ahead of all real ALU work.

**What the ISA says** (Table 66 'SOPK Opcodes' (p.240): 21 S_SETREG_IMM32_B32; ch.5 scalar-ALU instruction summary (p.~2373 in text dump): 'SOPK*' with literal note): S_SETREG_IMM32_B32  SOPK*  S_SETREG where 32-bit data comes from a literal constant (opcode 21 in Table 66)

**Suggested fix:** In the SOPK branch, extract the opcode ((w >> 23) & 0x1Fu) and when it is 21 set has_literal, literal = code[1], len_dwords = 2 (guarded by max_dwords >= 2).

**Verifier corrections/refinements:** Line 493 and the suggested fix are correct (extract op = (w >> 23) & 0x1F in the SOPK branch; when op == 21 set has_literal, literal = code[1], len_dwords = 2 guarded by max_dwords >= 2 — the existing one_plus_lit helper does exactly this). Severity should be LOW, not medium: rdna2_to_spirv.cpp:3089 already rejects SOPK opcode 21 fail-visibly (default: ok=false), and because translation walks the stream in order the shader containing s_setreg_imm32_b32 fails to recompile regardless of the desync, so no silently wrong rendered output is possible today. The concrete present-day impact is limited to desynced stream-level analyses and tooling (rdna2_sload_required_bytes, the constant-fold/dead-code scans, shader_inspect disassembly showing a phantom instruction at the literal's PC), plus a latent trap if SOPK 21 is ever implemented in stage 2. The finding's claim that compiler prologs commonly emit s_setreg_imm32_b32 for MODE is unproven for the exercised PS5 titles (no capture/test evidence in-repo; MODE programming has not surfaced as a recompile failure), which further supports low severity.

**When a real shader hits this:** No current title evidence of the encoding: no test, dump, or issue in-repo references s_setreg_imm32_b32, and a live shader containing it would already fail recompilation loudly via the stage-2 SOPK default reject (making it discoverable), which has not been reported. If a title's shader prolog does emit it (plausible for MODE round/denorm programming), the observable symptom today would be a rejected shader plus garbled shader_inspect/analysis output after the instruction — not wrong pixels. The fix is cheap and removes a future silent-desync trap.

### 6. [LOW] VOP3B carve-out incomplete: v_add/sub/subrev_co_u32 (0x30F/0x310/0x319), v_mad_i64_i32 (0x177), v_div_scale_f32/f64 (0x16D/0x16E) have SDST[14:8] misread as ABS bits and no sdst decoded

**Location:** `prosper/src/gpu/rdna2_decode.cpp:283`

**What the code does:** Only opcodes 0x128/0x129/0x12A/0x176 get the VOP3B treatment (sdst = bits [14:8], abs/clamp cleared). The remaining VOP3B-only opcodes decode as VOP3A: their scalar carry/flag destination bits [14:8] are misinterpreted as ABS[10:8] source modifiers and the sdst operand is left None. Latent today because stage 2 rejects these opcodes as unimplemented (and its analyses explicitly work around 'the decoder does not expose their sdst', rdna2_to_spirv.cpp:1926-1927) — but v_add_co_u32 e64 is the standard RDNA2 64-bit address-math op, so the first implementation attempt would silently read bogus abs modifiers and lose the carry-out.

**What the ISA says** (Section 13.3.4 VOP3B (p.260): exclusive opcode list; Table 84 'VOP3B Fields': SDST [14:8]; Table 85 'VOP3B Opcodes': 365/366/374/375/783/784/793): This encoding allows specifying a unique scalar destination, and is used only for the opcodes listed below: V_ADD_CO_U32, V_SUB_CO_U32, V_SUBREV_CO_U32, V_ADDC_CO_U32, V_SUBB_CO_U32, V_SUBBREV_CO_U32, V_DIV_SCALE_F32, V_DIV_SCALE_F64, V_MAD_U64_U32, V_MAD_I64_I32. SDST [14:8] Scalar destination. (Table 85: V_DIV_SCALE_F32=365, F64=366, V_MAD_U64_U32=374, V_MAD_I64_I32=375, V_ADD_CO_U32=783, V_SUB_CO_U32=784, V_SUBREV_CO_U32=793.)

**Suggested fix:** Extend the opcode set at rdna2_decode.cpp:283 to {0x128,0x129,0x12A,0x16D,0x16E,0x176,0x177,0x30F,0x310,0x319} (all VOP3B ops), keeping the sdst decode + abs/clamp clearing. Note VOP3B CLMP[15] is architecturally valid, so clearing clamp is itself a simplification worth a comment.

**Verifier corrections/refinements:** No corrections needed. File/line (rdna2_decode.cpp:283), opcode list, severity (low — latent, since stage 2 currently rejects all six opcodes as unimplemented), and the suggested fix are accurate. Minor addendum: rdna2_to_spirv.cpp cannot_write_vcc (line 1954) treats VOP3 opcodes 0x140-0x2FF as having no scalar carry dest, which would misjudge 0x16D/0x16E/0x177 (their SDST can be VCC) — also currently harmless because those opcodes fail translation, but worth fixing together with the decode extension so the analysis window logic keys off the decoded sdst instead of opcode ranges.

**When a real shader hits this:** Not exercised today: all six affected opcodes (0x16D/0x16E/0x177/0x30F/0x310/0x319) have no stage-2 handler, so any shader containing them fails recompilation fail-visibly and no wrong output is produced. The defect becomes live the moment anyone implements these ops — v_add_co_u32 e64 is the canonical RDNA2 64-bit address-add emitted pervasively by compilers for buffer/pointer math in compute shaders, and v_div_scale_f32/f64 are required for correct f64/precise-f32 division — at which point the implementation would silently read bogus abs modifiers and have no decoded carry-out destination.

### 7. [LOW] DS GDS bit not decoded: a GDS-flagged DS operation silently executes against workgroup LDS

**Location:** `prosper/src/gpu/rdna2_decode.cpp:406`

**What the code does:** DS decode extracts opcode (w>>18), the 16-bit offset (w&0xFFFF) and the VGPR fields, but never reads the GDS flag (bit 16 per the doc's Table 94; the code's own llvm-mc round-trips confirm OP occupies [25:18], leaving the GDS bit in the [16]/[17] gap that the decoder ignores either way). A whitelisted opcode with GDS=1 — e.g. ds_append/ds_consume used as a device-wide GDS append counter, or ds_add_u32 gds — decodes identically to its LDS form and rdna2_to_spirv.cpp:4737ff executes it against the per-workgroup LDS array, silently giving per-workgroup instead of device-global counter semantics.

**What the ISA says** (RDNA 2 ISA Reference Guide, Table 94 'DS Fields' (sec. 13.5, p.270) and sec. 12.13 DS_CONSUME/DS_APPEND (opcodes 61/62, p.196)): Table 94: 'GDS [16]: 1=GDS, 0=LDS operation.' 12.13 DS_CONSUME/DS_APPEND: 'This op can be used in both the LDS and GDS. In the LDS this address will be an offset to HWBASE ..., but in the GDS the M0.base constant will have the physical GDS address ... In GDS it is for the traditional append buffer operations.'

**Suggested fix:** Decode the GDS flag (store it on Rdna2Inst) and reject (ok=false) any DS instruction with GDS=1 in the emitter, keeping GDS operations fail-visible until a global-data-share model exists.

**Verifier corrections/refinements:** The actual gfx10 GDS bit is [17], not [16]: llvm-mc gfx1030 encodes ds_add_u32 (LDS) as 0xd8000000 and ds_add_u32 gds as 0xd8020000 (delta = bit 17), consistent with OP at [25:18]; Table 94's "GDS [16] / OP [24:17]" is an ISA-doc erratum (it leaves bit 25 unaccounted). Suggested fix accordingly: decode dword0 bit 17 as the GDS flag onto Rdna2Inst (optionally reject bit 16 too for fail-safety against the doc ambiguity) and set ok=false in the DS emitter when GDS=1. File/line correct (DS decode case spans rdna2_decode.cpp:401-413; the affected extraction starts at line 406); severity low is correct.

**When a real shader hits this:** Not exercised by any currently rendered title path as far as known: GDS appears in game shaders essentially only via driver-generated streamout/ordered-append or explicit global append counters, and prosper's exercised Messenger/Dead Cells/Blasphemous 2 shaders use only the whitelisted LDS forms (the DS whitelist itself was built from observed opcodes). A real shader would hit this only if a compute kernel used ds_append/ds_consume/ds_add_u32 with gds — then results would be silently per-workgroup instead of device-global, a hard-to-diagnose data corruption. Until then it is latent.

## gpu-audit ISA sweep: scalar ALU SCC semantics - 8 findings (missing/stale SCC writes) (#879)

### 1. [MEDIUM] s_not_b32 omits SCC = (result != 0)

**Location:** `prosper/src/gpu/rdna2_to_spirv.cpp:2765`

**What the code does:** SOP1 case 0x07 (s_not_b32) computes d = ~a and returns without writing rs.scc, so a following s_cbranch_scc0/1 or s_cselect consumes whatever SCC an earlier instruction produced.

**What the ISA says** (RDNA2 ISA 12.3 SOP1 Instructions, opcode 7 S_NOT_B32 (p.110-111)): "D = ~S0; SCC = (D != 0)."

**Suggested fix:** After d = b.iun(Op_Not, a), set rs.scc = b.ucmp(Op_INotEqual, d, b.uconst(0)) (same scc_nz form the SOP2 logical ops use).

**Verifier corrections/refinements:** Finding is accurate as written. Minor precision: the case label is line 2765 and the computation is line 2766. The suggested fix is right but note scc_nz is a lambda local to the SOP2 handler (line 2863); the SOP1 case should inline the equivalent: after d = b.iun(Op_Not, a), add rs.scc = b.ucmp(Op_INotEqual, d, b.uconst(0)). Do NOT add SCC to the adjacent s_brev_b32 case 0x0b — S_BREV_B32 has no SCC write in the ISA.

**When a real shader hits this:** Hit whenever a shader executes s_not_b32 and the next SCC producer comes after an SCC consumer — e.g. s_not_b32 followed by s_cselect_b32/b64 or s_cbranch_scc0/1. Compilers usually emit s_cmp_* immediately before SCC consumers, so the stale-SCC window is exercised only occasionally (bitmask-inversion + branch idioms), but when hit it silently selects the wrong branch/operand. Medium severity is appropriate.

### 2. [MEDIUM] 64-bit mask ops leave SCC stale; non-adjacent SCC consumers silently use it

**Location:** `prosper/src/gpu/rdna2_to_spirv.cpp:2825`

**What the code does:** The SOP2 mask family (0x0f..0x1d, line 2820+) and every SOP1 mask op (s_mov_b64/s_not_b64/s_wqm_b64/saveexec, comments at 2634-2635, 2824-2825) deliberately do not write rs.scc (the ISA's SCC is a cross-lane reduction). The linearizers only cover consumers ADJACENT to the producer: mask_test_branches requires the mask op to immediately precede the scc branch (line 1613), waterfall_branches walks back only for backward branches. A forward s_cbranch_scc0/scc1 (or an s_cselect) separated from its mask-op SCC producer by even one VALU op is instead structured by detect_forward_ifs on rs.scc — which still holds the bool from an EARLIER s_cmp/SOPC, so the branch/select silently evaluates a stale condition.

**What the ISA says** (RDNA 2 ISA, 12.4 SOP2 opcode 15 S_AND_B64 (and family): "D = S0 & S1; SCC = (D != 0)"; 12.3 SOP1 opcodes 36-55 saveexec: "SCC = (EXEC != 0)"; 12.5 opcode 4 S_CBRANCH_SCC0: "if(SCC == 0) then PC = PC + signext(SIMM16*4) + 4"): Every 64-bit mask logical/saveexec/wqm/not op overwrites SCC with (result != 0); a following s_cbranch_scc or s_cselect reads that value, not the last s_cmp's.

**Suggested fix:** Have the mask ops poison rs.scc (e.g. set a sentinel that makes any later SCC read reject fail-visibly, or set rs.scc = 0 id so spirv emission fails), unless the consuming branch is one the linearizers claimed; alternatively extend the walk-back recognition used by waterfall_branches to forward scc branches.

**Verifier corrections/refinements:** Finding is accurate; line 2825 (SOP2 mask block comment) is correct. Two extensions strengthen it: (a) even an ADJACENT forward scc branch is unprotected when the producer is s_orn2/nand/nor/xnor_b64 (SOP2 0x17/0x19/0x1b/0x1d), s_not_b64 (SOP1 0x08) or s_wqm_b64 (SOP1 0x0a) — mask_test_branches (line 1613-1617) recognizes only SOP2 0x0f/0x11/0x13/0x15 and SOP1 0x24/0x25/0x37; (b) s_cselect_b32 (line 2900) and s_cselect_b64 (line 2814) consumers have NO linearizer protection at any distance. Suggested fix stands: have the emit_alu mask ops set an scc-poisoned sentinel that any rs.scc read (detect_forward_ifs emission at 6258/6613, cselect at 2814/2900, SCC scalar source at 2577, s_addc carry-in at 2881) rejects fail-visibly, clearing the sentinel on any real SCC writer; branches claimed by the linearizers are unaffected.

**When a real shader hits this:** Currently latent for exercised titles: the covered shapes (adjacent kill-mask branch, backward waterfall) were derived from live captures (Messenger #102, DOLL #273) and match observed compiler output, and known Dead Cells fragment failures were VCC loops, not this. A shader hits it when the compiler schedules any instruction between a mask op and its forward scc branch, uses one of the uncovered mask opcodes adjacent to a scc branch, or consumes mask-op SCC via s_cselect — plausible in future/other-title shaders; the result is a silently wrong uniform branch/select (medium severity as filed).

### 3. [MEDIUM] s_max_i32/u32 SCC uses non-strict >= where ISA pseudocode is strict >

**Location:** `prosper/src/gpu/rdna2_to_spirv.cpp:2898`

### 7. [LOW] s_bfe_u64 lacks the width clamp: width 0 or offset+width > 64 emits undefined SPIR-V shifts

**Location:** `prosper/src/gpu/rdna2_to_spirv.cpp:2932`

**What the ISA says** (RDNA2 ISA 12.1 SOP2 Instructions, opcode 41 S_BFE_U64 (p.105)): "D.u64 = (S0.u64 >> S1.u[5:0]) & ((1 << S1.u[22:16]) - 1); SCC = (D.u64 != 0)" — defined for every 7-bit width value, producing 0 when the width is 0.

**Suggested fix:** Clamp before calling bfe_u64: cnt' = umin(cnt, 64-off), and special-case cnt==0 (or fold it into the shift math with a select) so the emitted shifts stay < 64, mirroring bfe_clamp_cnt.

**Verifier corrections/refinements:** Finding is accurate as filed. Line 2932 is the exact bfe_u64 call site; the root fix belongs in the helper bfe_u64 (rdna2_to_spirv.cpp lines 322-331) or its caller. **When a real shader hits this:** Effectively never in practice: s_bfe_u64 operands are compiler-generated literals with width in [1,64] and off+width<=64 (all observed uses in this repo's tests use off=32/40, width=8). *Independently reported by both the `scalar-alu` and `operands-builder` reviewers.*

Under round-to-nearest, 0.0 - (+0.0) = +0.0, so neg of a +0 input yields +0 instead of hardware's -0 (sign-bit flip); combined with abs, -|x| of any zero produces +0 where hardware produces -0. Downstream sign-of-zero-sensitive ops diverge: v_rcp gives +Inf instead of -Inf, packed/exported sign bits are 0, v_cmp_class and the ISA's min/max +-0 ordering rules see the wrong sign. NaN handling also differs (FSub may produce a new/quieted NaN vs a pure sign flip). Harmless in compares themselves (+0==-0), so the arithmetic uses are the exposure.

**What the ISA says** (RDNA2 ISA sec 6.2 p.43 ('applying absolute value (ABS field) or negate (NEG field) to any of the input operands'); Table 79 VOPC fields: 'NEG = Floating-point negation'; sec 12.7 V_MIN/MAX_F32 pseudocode's explicit +0.0/-0.0 cases show +-0 are architecturally distinct): NEG is floating-point negation of the source operand — a sign inversion, so neg(+0.0) = -0.0 and neg(NaN) flips only the sign bit.

**Suggested fix:** Replace the FSub(0,x) idiom with OpFNegate (a proper sign inversion in SPIR-V), or XOR the raw bits with 0x80000000; a single shared fneg helper in SpirvCompute fixes all 13 sites at once.

**Verifier corrections/refinements:** Finding is accurate. Minor completions: the full 13-site list is lines 2965, 3001, 3119, 3204, 3310, 3312, 3415, 3465, 3467, 3527, 3644, 3665, 3782 (the finding named 9 explicitly; the remaining four are the SDWA VOP1/VOP2 modifier paths at 3119/3204/3310/3312). Fix note: the SpirvCompute Op enum (line 30) lacks OpFNegate, so it must be added (SPIR-V OpFNegate = 127, defined as sign-bit inversion in current SPIR-V); alternatively XOR the raw bits with 0x80000000 (0x8000 for the unpacked-f16 paths at 2965/3415/3527/3665, which operate on f32-domain values after unpack_half, so 0x80000000 applies there too). Bit-XOR is the unconditionally correct option since Vulkan without SignedZeroInfNanPreserve does not formally guarantee FNegate preserves zero sign either.

**When a real shader hits this:** Manifests only when a NEG-modified source is exactly +0.0 and the result feeds a sign-of-zero-sensitive consumer: v_rcp/v_rsq of the negated value (+Inf instead of -Inf), sign-bit extraction/packing before export, v_cmp_class sign classes, or the ISA's min/max +-0 ordering rules. Plausible in real shaders (e.g. negated texcoords/directions that hit an exact zero, atan2-style math, cubemap coordinate negation at line 3782 on face boundaries), but rare per-pixel and usually visually minor; it will not corrupt typical arithmetic since -(+0) = +0 is value-equal in ordinary adds/muls/compares. Medium is the right severity: silently wrong in edge cases, correct for all nonzero finite inputs.

*Independently reported by both the `vopc-mods` and `vector-alu` reviewers.*

But the finding does not survive scrutiny on reachability or wrongness. (1) The claim "dropped without any reject" is partially false: a shader whose only position export is target 16 leaves `exported` false and is rejected fail-visibly at line 7078 (`if (!exported) return {};`). (2) In the only ISA-legal shape — §11.2.2 (p. 99) mandates "Every vertex shader must output at least one position vector ... to the POS0 target" — POS4 is ancillary alongside POS0, and the code already silently drops ALL secondary position exports (targets 13..15, or any position export after the first) via the `!exported` condition; that single-position model is the existing deliberate approximation (ancillary channels like POS1..3 clip distances are equally dropped), a missing-feature/approximation the audit brief excludes, not a target-16-specific decode error. - **[exec-cf] Compute-execz VCC-clobber guard undercounts 64-bit scalar write widths** - The code description is accurate: the local width model at prosper/src/gpu/rdna2_to_spirv.cpp:2326-2328 (SOP1 width 2 only for 0x04, SOP2/SOPK always 1) is narrower than the shared scalar_write_width at line 2406, which correctly gives width 2 to SOP1 0x08/0x0a/0x1f/0x24/0x25/0x37 and the SOP2 B64 ops. However, the claimed failure scenario is architecturally unencodable: RDNA 2 ISA section 3.6.3 "SGPR Alignment" requires "Even-aligned SGPRs ... When 64-bit data is used", and the SALU chapter states "If an instruction uses 64-bit data in SGPRs, the SGPR pair must be aligned to an even boundary ... legal to use SGPRs 2 and 3 or 8 and 9 (but not 11 and 12)". VCC_LO is SGPR 106 (even), so a B64 write based at s105 (the finding's `s_and_saveexec_b64 s105` example, s105:s106 overlapping VCC_LO) is illegal; a legal B64 destination either ends at s104:s105 (no VCC overlap) or is based exactly at VCC (106). In the base=106 case the guard still fires even with width 1 — dst.value=106 falls inside [106,107) — so the sgpr_dead_at_merge(106) proof is still required and the arm is not silently admitted. The only real gap is the skipped proof for the VCC_HI half (107) of a VCC-based B64 write. That gap has no plausible wrong-result path: the missed opcode classes are mask-domain ops that emit_alu models per-lane in sreg_bool (s_not_b64/s_wqm_b64/saveexec/s_cselect_b64 handled at lines 2611-2825) and the structured-if phi machinery merges boolean/EXEC state at the merge (lines 2127, 6640), so the scalar model CAN reconstruct them — the guard's comment explicitly scopes the concern to integer-domain scratch writes into VCC (the UE4 s_mov_b32 vcc_lo shape, which width 1 catches). Unsupported forms reject fail-visibly. The only escaping integer-domain 64-bit VCC write would be a shape like `s_getpc_b64 vcc` inside a compute execz arm followed post-merge by a 32-bit redefinition of vcc_lo only and then an implicit VCC read — a sequence no compiler emits, and sgpr_dead_at_merge (line 1429) already flags implicit VCC readers for both halves, so the two halves' proofs diverge only in that contrived partial-redefinition case. Harmonizing on scalar_write_width would be strictly more conservative and is reasonable hygiene, but the finding's asserted defect — admitting an arm whose VCC clobber the model cannot reconstruct — does not occur on any encodable, plausibly-emitted path.
